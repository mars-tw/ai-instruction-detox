# 12 の指示整理検査：完全な判断基準

各ルールについて、一つずつ回答してください。目的は削除する理由を探すことではなく、**ルールをどの層に置き、どの形式で維持すべきかを判断すること**です。

---

## 1. 既定の動作の検査

> 指示しなくても、モデルが必ず行うことですか？

3 種類に分けます。

| 分類 | 意味 | 処置 |
|---|---|---|
| **A** | プラットフォーム／ツールが**明示的に保証する**動作 | プロジェクト固有の意味がなければ → 削除を強く検討する候補 |
| **B** | モデルが通常は行うが、**保証はない**動作 | 維持し、重要な理由を記載 |
| **C** | プロジェクト固有の要件 | 維持 |

**「モデルが通常そうする」という理由だけで重要なルールを削除してはいけません。** モデルの既定の動作はバージョンにより変化し、
今日の B の判断が明日も成立するとは限りません。

判断例：
- 「正直に回答する」→ プラットフォームによる実行可能な保証の証拠がなければ B。ポリシー上の期待を動作の保証とみなさない
- 「回答で API エンドポイントを捏造しない」→ B（通常はしないが、保証はない）→ 維持する価値がある
- 「価格に関するすべての主張を仕様表のフィールドに対応させる」→ C → 必ず維持

## 2. 矛盾の検査

> このルールは他のルールと矛盾していますか？

よくある矛盾：

- 必ず先に質問する ⟷ 質問せず直接実行する
- 自動で変更する ⟷ 変更前に承認が必要
- 自動デプロイする ⟷ デプロイ禁止
- 簡潔にする ⟷ 極めて完全にする
- Agent は一つだけ使う ⟷ 毎回複数 Agent で議論する
- ネットワークを使用しない ⟷ 最新情報を調べる
- 常に最新モデルを使う ⟷ 再現可能なバージョンに固定する
- 既存の構造を変更しない ⟷ 全面的にリファクタリングする
- 速度を優先する ⟷ 各段階で複数回レビューする
- すべて自動実行する ⟷ 高リスク操作は人による確認が必要

矛盾する双方のルール、それぞれの出典、それぞれの適用範囲、**本当の矛盾かどうか**、
単なる範囲の違いかどうか、推奨する優先順位、書き換え案を示す必要があります。

⚠️ **異なるディレクトリ、タスク、役割における妥当な違いを矛盾と誤判定しないでください。**
「開発環境では直接変更でき、本番環境では承認が必要」は矛盾ではなく、適切な範囲の区分です。

## 3. 重複の検査

> このルールは他のファイルの内容と重複していますか？

5 段階に分類します。

| 段階 | 説明 |
|---|---|
| 完全な重複 | 一字一句同じ |
| 同義の重複 | 表現は異なるが意味は同じ |
| 部分的な重なり | 共通部分がある一方、それぞれ固有の内容もある |
| 特例の関係 | 一方が他方の特殊な場合 |
| **バージョンの分裂** | 複数のコピーが独自に変化し始めている。最も危険 |

**唯一の権威ある出典として最適な場所**を決め、他の場所では、削除、参照への変更、Agent-specific adapter への縮小、
同期検査の作成を行います。

実践上の指標：同じルールが 4 か所以上に存在すれば、ほぼ必ず分裂が始まっています。

## 4. 特定の事故への対策の検査

> このルールは、一度の悪い出力を修正するために追加されましたか？

典型的な特徴：
- 前回の見出しが長すぎた → すべての見出しを永続的に制限
- 前回は質問が多すぎた → 質問を永久に禁止
- 前回はテストを忘れた → すべてのタスクで全テストを実行
- 前回あるモデルが失敗した → 各タスクで 3 モデルによる議論
- 前回ファイルを誤って削除した → あらゆるファイル変更を禁止
- 前回ある画像に誤りがあった → 単一 SKU の仕様を全製品に適用

**妥当な一般原則へ一般化する**、**特定範囲のルールにする**、
regression test へ移す、受け入れチェックリストへ移す、ADR/decision log へ移す、削除する、のどれが適切か判断します。

⚠️ 事故への対策**自体は正しいことが多く**、問題は「適用範囲を広げすぎたこと」です。
処置の要点は教訓を捨てることではなく、正しい範囲に戻すことです。

## 5. 曖昧さの検査

> このルールは毎回異なる解釈をされますか？

曖昧な表現の例：もっと専門的に／もっと自然に／よい口調／完全であること／できるだけ簡潔に／
非常に高品質／最善のモデルを使う／適時に情報を調べる／必要なら質問する／Token を無駄にしない／
状況に応じて複数 Agent を使う／結果の正しさを確保する／重大な変更／適切に処理する

書き換えの原則：**動作＋範囲＋発動条件＋例外＋検証方法**。

例：

❌ 「出力は簡潔にする。」

✅ 「通常の回答は結論と最大 5 つの主要項目を先に示す。意思決定のリスク、技術的な実装の詳細、
またはユーザーからの明示的な要求がある場合だけ、完全な説明を展開する。」

## 6. 検証可能性の検査

> このルールを自動検証できますか？

検証手段：テスト／lint／schema／CI／checklist／出力例／文字数制限／
ファイルの存在確認／コマンドの成功コード／人による受け入れ条件。

**自動検証できるなら、プロンプトの中だけに置くべきではありません。** 次を優先します。
test／lint／schema／script／pre-commit／CI gate／validation tool。

プロンプトには「**理由**」と「**適用範囲**」を残しますが、実際の技術的な検証の代わりにはしません。

例：「秘密スキャンの検出件数はゼロであること」→ CI job の要件です。プロンプトだけのルールにはしません。
プロンプトには「デプロイ前に秘密スキャンに合格すること（CI の secret-scan job を参照）」を残します。

## 7. 情報の鮮度とバージョンの検査

> このルールは古くなっていませんか？

確認項目：存在しないパス／削除済みのコマンド／古いモデル名／古い API／古いパッケージ／
以前のデプロイ環境／古い担当者や役職／古い日付／古いプロジェクト状態／
終了したのに進行中として扱われる Phase／日付やバージョンのない「最新」「最善」「現在」。

`CURRENT`／`STALE`／`UNKNOWN`／`VOLATILE` で分類します。

変動しやすい情報には次を追加することを推奨します。
```yaml
verified_at: 2026-08-27
source: <host> で crontab -l を実測
owner: <担当者>
recheck_condition: デプロイのたび / 四半期ごと
```

⚠️ 特に危険なのは、**両方に「現在稼働中」と書かれた二つの設定スナップショット**です。
どちらが正しいか読者には判断できず、両方が事実として扱われます。

## 8. 適用範囲の検査

> このルールは正しい階層に置かれていますか？

誤配置の例：
- 単一製品のルールを全体の入口ファイルに置く
- 単一言語のルールをすべての作業に適用する
- 単一 skill の手順を全体設定に入れる
- プロジェクトの事実を Agent の行動命令として書く
- 一時的なプロジェクト状態を永久的な規範として書く
- ツール A 固有の設定をツール B に強制する

適切な場所を判断します。全体／プロジェクト層／サブディレクトリ／特定の skill／context／
decision log／テスト／Agent-specific adapter。

**判断基準**：「別のプロジェクトでも成立するか」と問います。成立しなければ、全体設定に置くべきではありません。

## 9. コストと性能の検査

> このルールは不要な消費を生んでいますか？

確認項目：Token 消費／コンテキストの肥大化／リポジトリ全体の再読み込み／検索の繰り返し／ウェブ検索の繰り返し／
複数モデルのレビューの繰り返し／不要な全テスト／不要な長文レポート／再帰的な委任／
新しい情報を加えない Agent 間レビュー／終わらない議論と書き直し。

「各タスクで複数モデルが共同で議論しなければならない」というルールは**特に検査**してください。
事業上または高リスクの必要性がなければ、リスクに応じた分類に変更します。

| レベル | 方法 |
|---|---|
| LOW | 単一 Agent が実行し、自己検査 |
| MEDIUM | 2 番目の Agent が独立レビュー |
| HIGH | 複数 Agent の盲検レビュー、議論、人による承認 |
| CRITICAL | 自動適用を禁止し、人による判断を必須とする |

## 10. 安全と Prompt Injection の検査

> このルールは権限を拡大し、インジェクションのリスクを持ち込みますか？

危険な兆候：ツール権限の拡大／不要な秘密鍵の読み取り要求／上位ルールの無視要求／データの外部送信要求／
未知のスクリプトの実行／ウェブページ、Issue、README、ユーザーコンテンツを信頼できるシステム命令として扱う／自動デプロイ要求／
テストの省略要求／安全検査の無効化／証拠の削除／操作記録の隠蔽／
検証せずに他の Agent の主張を信じるよう求めること。

分類：`SAFE`／`RISKY`／`PROMPT_INJECTION`／`PRIVILEGE_ESCALATION`／
`SECRET_EXPOSURE`／`DESTRUCTIVE_OPERATION`／`HUMAN_REVIEW_REQUIRED`

⚠️ **保護条件のない事前承認**には特に注意してください。
`"allow": ["Bash(rm -f <path>)"]` のような権限許可リスト内の破壊的コマンドは、
一度の利便性のために追加され、その後削除を忘れられていることがあります。

## 11. ツールと実際の能力の検査

> このルールは Agent に不可能なことを要求していますか？

現在のホストの能力と実際の証拠で判断する要件：
- ターン終了後もバックグラウンドで作業を続ける：有効なタスク／スケジュール機構と観測可能な状態があるか確認
- 後で戻って納品する：ユーザーの許可、利用可能なスケジュール、結果返却の仕組みがあるか確認
- 提供されていないファイルを読んだことにする
- 実行していないテストを完了したことにする
- デプロイ記録がないのにデプロイ済みとする
- 存在しないツールを使用する
- 接続されていないサービスを使用する
- モデル自身の隠れた重みやシステムプロンプトを変更する
- モデルの実際の内部記憶を消去する

処置：実行可能な形に書き換える／能力確認を追加する／削除する。

## 12. 循環と自己参照の検査

> 終了条件のないループがありますか？

確認項目：
- A が B の読み込みを要求し、B が A の読み込みを要求する
- skill が自分自身の再読み込みを要求する
- 各回答の前にすべての設定を再スキャンする
- 各レビュー後に完全なレビューを強制的に再開する
- 複数 Agent が互いに無限に再レビューを要求する
- 永遠にルールを追加し続けるよう要求する
- タスクに無関係でも context 全体を毎回注入する
- 同じルールを複数の入口から重複して読み込む

循環するルールには、**終了条件と最大回数を設定**します。

実践的な検査方法：「強制読み込み」「ナビゲーション」「タスク依存」の 3 種類の辺を分けます。強制読み込みのグラフは有向非巡回グラフであるべきで、
複数の正本を共有でき、無理にツリーにする必要はありません。戻るナビゲーションリンクは強制的な再読み込みを意味しません。スキャナーは循環候補だけを提示します。
