# 複数 Agent によるレビュー手順

---

## 2 つ以上の**本当に独立した**モデルがある場合

### 第 1 段階：盲検レビュー

| 役割 | 作業 | 制限 |
|---|---|---|
| Auditor A | ファイルの棚卸し、ルールの原子化、矛盾と重複の分析 | **先に B の結論を見ない** |
| Auditor B | 同じ監査を独立して実行 | **先に A の削除案を見ない** |

### 第 2 段階：相互レビュー

二つの結果を比較し、次を探します。
- A は削除、B は維持を提案したルール
- A は矛盾、B は範囲の違いと判断したルール
- **双方が見落としたルール**（最も価値のある発見）
- 安全、デプロイ、データの完全性について判断が異なる箇所
- 「一度の対策か一般ルールか」の判断が異なる箇所

### 第 3 段階：ガバナンスの裁定

統合担当が最終案を作成します。**重大な意見の相違については双方の理由を維持し、合意済みと装ってはいけません。**

---

## Agent が一つだけの場合（よくある状況）

焦点を変えて 2 回レビューします。

| 回 | 焦点 | 方針 |
|---|---|---|
| 1 回目 | 完全性と維持 | 多めに残し、ルールの見落としがないことを先に確認 |
| 2 回目 | 簡素化、矛盾、コスト | 重複、矛盾、古い情報、肥大化を積極的に探す |

**次のように明示する必要があります。**

> これは単一モデルによる、焦点の異なる 2 回のレビューです。**二つの独立したモデルによる盲検レビューではありません。**

### 絶対的な禁止事項

**単一 Agent の 2 回の自己レビューを、独立した第三者検証と説明してはいけません。**

これは誠実さの最低条件です。2 回の自己レビューには価値があります。2 回目で 1 回目の見落としを見つけることもありますが、
同じ偏りを共有しており、独立した検証とは同等ではありません。

---

## 実践上の推奨：領域ごとの並行監査

ルールが数百件ある場合、単一 agent の出力は制限を超えます。次のように分割することを推奨します。

```
領域 A：ユーザー層の入口ファイル + 設定ファイル
領域 B：最大のプロジェクト指示ファイル（さらに分割が必要な場合がある）
領域 C：その他のプロジェクトファイル + 記憶ファイル
領域 D：ファイル間の矛盾と重複の探索（A/B/C の間の矛盾を専門に探す）
領域 E：安全、インジェクション、能力、循環（危険な種類を専門に探す）
領域 F：completeness critic（「全員が見落とした位置」を専門に探す）
```

**領域 F は省かれやすい一方、発見するものは最も重要なことが多くあります。**
例えば全員が `CLAUDE.md` を監査し、隣に同じくらい大きな `AGENTS.md` があることに誰も気付かない場合です。

### 出力上限を超えた場合

一つの領域にルールが多すぎ、出力が打ち切られた場合：
1. **完了したと装わない**
2. 分割方式に変更する（例：節ごとに 3 分割）
3. レポートに「ある領域は未完了のため、分割して補完中」と正直に記載する
4. 補完が完了したら結果を反映し、検証項目を更新する

## 相互レビューでの裁定原則

二つの監査結果が異なる場合：

| 状況 | 採用する判断 |
|---|---|
| 一方に実測の証拠があり、他方は推測 | **証拠がある判断** |
| 一方が「安全」、他方が「リスクあり」 | **厳しい判断**（リスクがないことを証拠で示せる場合を除く） |
| 一方が重複、他方が範囲の違いと判断 | ルールの範囲と正本を見る。同時読み込みは重複コストを生み、異なる session にある同じルールのコピーもバージョン分裂を検査する。本当に異なる範囲だけを維持できる |
| 一方が削除、他方が維持を希望 | 削除側が代替ルールを示せない限り、既定では**維持** |

裁定の記録には、矛盾の内容、採用したルール、理由、置き換えられるルールの処置、
人による確認が必要かどうかを必ず記載します。

## 独立したコンテキストと異なるモデル

同じモデルの独立したコンテキストでもレビューできますが、異なるモデルによる検証とは呼びません。委任には必要なマスキング済みデータだけを渡し、
現在実際に利用可能で、許可された仕組みだけを使用します。未知のツールを起動せず、再帰的な委任や無限の相互レビューを行いません。
レビュー担当はファイルとテストの証拠を読み戻します。実行担当の完了宣言をそのまま信じてはいけません。
