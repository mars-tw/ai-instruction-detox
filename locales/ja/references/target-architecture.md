# 目標構造：整理後の形

---

## 4 つの基本原則

### 1. 唯一の権威ある出典

各ルールの主要な権威ある出典は**一つ**だけにします。他のファイルでは次だけを行えます。
参照／Agent-specific なアダプター／本当に異なる範囲の補足。

入口ファイル、skills、context に同じルールを一つずつコピー**しないでください**。

### 2. 入口ファイルには長期的な全体ルールだけを置く

置くべき内容：
- プロジェクトの使命と範囲
- 破ってはいけない中心的な制約
- 重要な構造原則
- 安全とデータ保護
- 主な開発コマンド
- テストと受け入れの最低要件
- 変更とデプロイの境界
- 指示の優先順位
- 関連する skill／context の読み込み方法
- 完了の定義

置く**べきでない**内容：
大量の履歴／一度の事故／特定タスクの完全な手順／大量の例／
終了した Phase の詳細／各タスクで不要な背景／頻繁に変わる担当者やバージョン情報。

目安は **80–200 行**です。超える場合は理由を説明し、**目安に合わせるために重要な内容を削除してはいけません**。

### 3. skills には繰り返し使うワークフローだけを置く

各 skill には、名称／目的／発動条件／発動すべきでない場合／必要な入力／
利用可能なツール／実行手順／リスクと制限／出力形式／受け入れ基準／停止条件／
失敗処理／他の skill との関係を含めます。

**すべての skill を毎回自動読み込みさせてはいけません。** 現在のタスクに直接関係するものだけを読み込みます。

### 4. context には事実と状態だけを置く

保存すべき内容：検証済みの事実／構造の状態／プロジェクトの基準／現在のバージョン／完了と未完了の項目／
用語集／役割とリソース／意思決定の根拠／出典と日付。

大量の恒久的な行動ルールを詰め込む**べきではありません**。

変わりやすい情報には次が必要です。
```yaml
verified_at: 2026-08-27
source: <実測方法または出典>
owner: <担当者>
expires_at / recheck_condition: <再検証条件>
```

## Agent 間で共有する構造

**問題**：Agent ごとに入口ファイルが異なり、同じ参照構文に対応しているとは限りません。

**方針**（どのツールについても特定の参照構文への対応を仮定しません）：

```
<共用目錄>/core-rules.md          ← プレーンテキスト。どの Agent でも読める
├── ルールの優先順位
├── 言語
├── 認証情報
├── 外向け文章のポリシー
├── CLI 間の委任
└── 実際に行っていないことを主張しない

各 Agent の入口ファイル（その Agent に本当に固有の違いだけを残す）
├── Claude:  そのツールが対応し、使用可能と検証済みの import 構文
├── Codex:   明示パスでの読み込み指示（「<path> を読み込み、従う」）
├── Qwen:    同上
└── Grok:    同上
```

**要点**：
1. 先に**現在の環境とプロジェクトでの実際の使用方法を確認**し、構文が使えると仮定しません。
2. 参照に対応していないツールでは、**避けられない最小限の内容**だけを重複させます。
3. 重複する部分には**同期検証を設けます**（下記参照）。
4. 各入口ファイルに `VERSION` を付け、分裂の有無を比較できるようにします。

## 一度の事故を記録する場所

| 性質 | 保存先 |
|---|---|
| 自動検証できる動作 | regression test |
| 納品前に必ず確認すること | acceptance checklist |
| 構造に関する決定 | ADR（Architecture Decision Record） |
| 事故の経緯と根本原因 | incident report |
| 判断した理由 | decision log |
| 純粋な履歴 | archive（読み込まない） |
| 特定ディレクトリでだけ成立 | そのディレクトリのルールファイル |

**すべての事故を全体の Agent 指示に永久に積み上げないでください。**

---

## ルールの書き方

各ルールにはできる限り、**動作／適用範囲／発動条件／例外／検証方法／失敗時の処理**を含めます。

判断基準のない表現は控えます。最善／完璧／高品質／自然／適切／状況に応じて／最新／優先／完全。

`MUST`／`NEVER`／`ALWAYS` は**特にレビュー**してください。本当に違反できない
安全、データの完全性、法令、中心的な受け入れ条件だけに絶対的な表現を使います。

---

## ルールの再蓄積を防ぐ

1. **唯一の権威ある出典という原則**を入口ファイル自体に記載
2. **入口ファイルの行数の目安**（ユーザー層 ≤ 40 行、プロジェクト層 ≤ 200 行）
3. **同期検査を自動化**し、次を検証するスクリプトを作成
   - 各入口ファイルが共通の正本を参照しているか
   - `VERSION` が一致するか
   - 重要なルールの文字列が正本だけに現れるか（重複なし）
   - 参照パスがすべて存在するか（参照切れなし）
4. **ルールの追加前に 3 点確認**
   - 正本はどこか（既に書かれていないか）
   - 自動検証できるか（可能ならテストにする）
   - 一般原則か、一度の事故か（後者なら範囲を狭める）
5. **記憶とスケジュールを四半期レビューの対象にする**。自動注入されるため、古いルールが最も蓄積しやすい種類です。

---

## 同期検証スクリプトが確認すること

```
[ ] 共通の正本が存在し、空でない
[ ] 共通の正本に必要な節がすべてある
[ ] 各入口ファイルが共通の正本を参照している
[ ] 入口ファイルが正本の内容を複写していない（重要な文字列が重複しない）
[ ] すべての参照パスが存在する（参照切れなし）
[ ] 循環参照がない
[ ] skill のリンク／junction が正しい対象を指している
[ ] デプロイ済みコピーと元の assets が同期している（hash 比較）
```

⚠️ **検証スクリプト自体も古くなります。** 入口ファイルの内容を「文字列の一致」で検査すると、
ルールの移動後に誤って失敗する場合があります。修正前に、**アサーションが古いのか、ルールの参照が実際に切れたのか**を確認します。
「**文字列**」（特定の文を含むか）ではなく「**機能**」（正本を参照するか）を検証するアサーションを推奨します。

## プロジェクトのメインスキルとサブスキル

プロジェクト全体の標準化を依頼された場合は、[プロジェクト整理手順](project-organization.md) に従ってメインスキルとワークフローを作成し、
各サブスキルを対応するサブプロジェクト内に置きます。project-map.json に唯一の階層とパスの索引を保存し、
ナビゲーション、パンくずナビゲーション、マインドマップを生成します。共通の正本とメインスキルは役割を分けます。正本はタスク横断の制限、
メインスキルはタスクの振り分けと引き継ぎを担当します。共通ルールを複写せず、すべてのサブスキルの読み込みを強制しません。
