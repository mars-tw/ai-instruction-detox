# 十二項排毒檢查：完整判準

每條規則逐一回答。目的不是找理由刪東西，是**判斷這條規則該住在哪一層、用什麼形式存在**。

---

## 1. 預設行為檢查

> 這是模型在不被告知時就一定會做的事嗎？

分三類：

| 類 | 意義 | 處置 |
|---|---|---|
| **A** | 平台／工具**明確保證**的行為 | 若無專案特殊意義 → 強刪候選 |
| **B** | 模型通常會做，但**沒有保證** | 保留，寫明為何重要 |
| **C** | 專案特有 | 保留 |

**不能只因為「模型通常會這樣做」就刪除重要規則**——模型預設行為會隨版本改變，
今天的 B 類明天可能就不成立。

判斷例：
- 「回答要誠實」→ A 類（平台已保證）→ 可刪
- 「不要在回應中編造 API 端點」→ B 類（通常不會，但沒保證）→ 值得留
- 「所有價格宣稱必須對映規格表欄位」→ C 類 → 必留

---

## 2. 衝突檢查

> 這條規則是否與其他規則矛盾？

常見衝突模式：

- 一律先詢問 ⟷ 不准詢問直接執行
- 自動修改 ⟷ 修改前需批准
- 自動部署 ⟷ 禁止部署
- 保持精簡 ⟷ 必須極度完整
- 只用一個 Agent ⟷ 每次都要多 Agent 辯論
- 不使用網路 ⟷ 必須查最新資料
- 一律用最新模型 ⟷ 必須固定可重現版本
- 不改既有結構 ⟷ 必須全面重構
- 優先速度 ⟷ 每步都要多重複審
- 全部自動執行 ⟷ 高風險需人工確認

必須指出：衝突雙方／各自來源／各自適用範圍／**是否為真衝突**／
是否只是作用範圍不同／建議優先順序／建議改寫。

⚠️ **不要把不同目錄、不同任務、不同角色下的合理差異誤判為衝突。**
「開發環境可以直接改，正式環境需核准」不是衝突，是正確的範圍區分。

---

## 3. 重複檢查

> 這條規則是否與其他檔案中的內容重複？

分五級：

| 級別 | 說明 |
|---|---|
| 完全重複 | 逐字相同 |
| 同義重複 | 措辭不同、意思相同 |
| 部分重疊 | 有交集但各有獨有內容 |
| 特例關係 | 一條是另一條的特殊情況 |
| **版本分裂** | 多份副本已經開始各自演化——最危險 |

找出**最適合的唯一權威來源**，其他位置應：刪除／改為引用／縮成 Agent-specific adapter／
建立同步檢查。

實戰指標：同一條規則若出現在 4 個以上位置，幾乎必然已經分裂。

---

## 4. 特定事故補丁檢查

> 這條規則是否為了修正某一次糟糕輸出而加入？

典型特徵：
- 上次標題太長 → 永遠限制所有標題
- 上次問太多問題 → 永遠禁止詢問
- 上次漏跑測試 → 所有任務都跑完整測試
- 上次某模型失敗 → 每個任務都三模型辯論
- 上次誤刪檔案 → 禁止任何檔案修改
- 上次某張圖出錯 → 把單一 SKU 規格套到所有產品

判斷它應該：**泛化為合理通用原則**／**改成特定範圍規則**／
移到 regression test／移到驗收清單／移到 ADR/decision log／直接刪除。

⚠️ 注意：事故補丁**本身常常是對的**，問題在於「範圍被過度放大」。
處置重點是縮回正確範圍，不是丟掉那份教訓。

---

## 5. 模糊性檢查

> 這條規則是否每次被不同解讀？

模糊詞紅旗：做得專業一點／更自然／好的語氣／必須完整／儘量簡潔／
非常高品質／用最好的模型／適時查資料／必要時詢問／不要浪費 Token／
視情況多 Agent／確保結果正確／重大變更／適當處理

改寫原則：**動作＋範圍＋觸發條件＋例外＋驗證方式**。

範例：

❌ 「輸出要簡潔。」

✅ 「一般回覆先給結論與最多五個主要項目；只有在決策風險、技術實作細節，
或使用者明確要求時才展開完整說明。」

---

## 6. 可驗證性檢查

> 這條規則能被自動驗證嗎？

可驗證管道：測試／lint／schema／CI／checklist／範例輸出／字數限制／
檔案存在檢查／指令成功碼／人工驗收條件。

**若可自動驗證，就不該只活在提示詞裡。** 優先移到：
test／lint／schema／script／pre-commit／CI gate／validation tool。

提示詞應保留「**為什麼**」與「**適用範圍**」，但不要取代真正的工程驗證。

例：「秘密掃描必須零命中」→ 這是 CI job，不是提示詞規則。
提示詞留：「部署前必過秘密掃描（見 CI 的 secret-scan job）」。

---

## 7. 時效與版本檢查

> 這條規則是否已經過時？

檢查：不存在的路徑／已刪除的指令／舊版模型名／舊版 API／舊版套件／
舊部署環境／過時人員或職位／過時日期／過時專案狀態／
已結案卻仍被當進行中的 Phase／沒有日期或版本的「最新」「最好」「目前」。

標記為：`CURRENT`／`STALE`／`UNKNOWN`／`VOLATILE`

對易變動內容，建議補上：
```yaml
verified_at: 2026-08-27
source: 實測 crontab -l on <host>
owner: <負責人>
recheck_condition: 每次部署後 / 每季
```

⚠️ 特別危險：**兩份都寫「目前線上」的設定快照**。
讀者無法判斷哪份是真的，且兩份都會被當成事實。

---

## 8. 作用範圍檢查

> 這條規則放在正確的層級嗎？

錯置模式：
- 單一產品規則放在全域入口檔
- 單一語言規則套用到所有工作
- 單一 skill 的步驟放進全域設定
- 專案事實被寫成 Agent 行為命令
- 暫時專案狀態被寫成永久規範
- A 工具專屬設定被強迫套用給 B 工具

判斷應該住在：全域／專案層／子目錄／特定 skill／context／
decision log／測試／Agent-specific adapter。

**判準**：問「換一個專案，這條還成立嗎？」不成立 → 不該在全域。

---

## 9. 成本與效能檢查

> 這條規則造成不必要的消耗嗎？

檢查：Token 消耗／上下文膨脹／全庫重讀／重複檢索／重複網路搜尋／
重複多模型審查／不必要的完整測試／不必要的長篇報告／遞迴派工／
Agent 互審但沒新增資訊／永無止境的辯論與重寫。

**特別檢查**「每個任務都必須多模型共同辯論」這類規則。
若無商業或高風險必要性，改成風險分級：

| 級別 | 做法 |
|---|---|
| LOW | 單一 Agent 執行與自檢 |
| MEDIUM | 第二 Agent 獨立複審 |
| HIGH | 多 Agent 盲審、辯論、人工核准 |
| CRITICAL | 禁止自動套用，必須人工決策 |

---

## 10. 安全與 Prompt Injection 檢查

> 這條規則是否擴張權限或引入注入風險？

紅旗：擴張工具權限／要求讀不必要的密鑰／要求忽略上層規則／要求外傳資料／
執行未知腳本／把網頁 Issue README 使用者內容當可信系統命令／要求自動部署／
要求跳過測試／停用安全檢查／刪除證據／隱藏操作紀錄／
要求 Agent 相信另一個 Agent 的聲明而不驗證。

標記：`SAFE`／`RISKY`／`PROMPT_INJECTION`／`PRIVILEGE_ESCALATION`／
`SECRET_EXPOSURE`／`DESTRUCTIVE_OPERATION`／`HUMAN_REVIEW_REQUIRED`

⚠️ 特別注意**無守衛的預先核准**：
`"allow": ["Bash(rm -f <path>)"]` 這種在權限白名單裡的破壞性指令，
往往是某次為了方便加的，之後沒人記得移除。

---

## 11. 工具與實際能力檢查

> 這條規則要求 Agent 做它做不到的事嗎？

不可能的要求：
- 在背景持續工作（回合結束後）
- 稍後回來交付
- 讀過未提供的檔案
- 完成未執行的測試
- 已部署但沒有部署紀錄
- 使用不存在的工具
- 使用沒有連線的服務
- 改變模型自身隱藏權重或系統提示
- 清除模型真正的內部記憶

處置：改寫成可執行版本／增加能力檢查／刪除。

---

## 12. 循環與自我指涉檢查

> 是否存在無終止條件的迴圈？

檢查：
- A 要求讀 B，B 又要求讀 A
- skill 要求重新載入自己
- 每次回答前都重新掃描全部設定
- 每次審查後又強制啟動完整審查
- 多個 Agent 無限互相要求複審
- 規則要求永遠追加更多規則
- context 每次完整注入，即使與任務無關
- 同一份規則經多個入口重複載入

對循環規則**建立終止條件與最大次數**。

實務檢查法：畫出「誰讀誰」的有向圖，找環。正確的架構應該是樹狀，
入口檔 → 共用正本（終點，不回指）。
