# 多 Agent 審查流程

---

## 若有兩個以上**真正獨立**的模型

### 第一輪：盲審

| 角色 | 做什麼 | 限制 |
|---|---|---|
| Auditor A | 檔案盤點、規則原子化、衝突與重複分析 | **不先看 B 的結論** |
| Auditor B | 獨立做相同審計 | **不先看 A 的刪除建議** |

### 第二輪：交叉審查

比較兩份結果，找出：
- A 建議刪、B 建議留的規則
- A 認為衝突、B 認為只是作用範圍不同的規則
- **雙方都忽略的規則**（最有價值的發現）
- 對安全、部署、資料完整性判斷不一致的部分
- 對「一次性補丁 vs 通用規則」判斷不同的部分

### 第三輪：治理裁決

由整合者產生最終提案。**對重大分歧保留雙方理由，不得假裝已達成共識。**

## 若只有單一 Agent（常見情況）

執行兩次不同焦點的審查：

| 輪次 | 焦點 | 傾向 |
|---|---|---|
| 第一次 | 完整性與保留 | 寧可多留，先確保沒有規則被漏掉 |
| 第二次 | 簡化、衝突與成本 | 積極找重複、矛盾、過時、膨脹 |

**必須明確標示**：

> 這是單一模型的兩次不同焦點審查，**不是兩個獨立模型的盲審**。

### 絕對禁止

**不得把單一 Agent 的兩次自審描述成獨立第三方驗證。**

這條是誠信底線。兩次自審有價值（第二輪確實會抓到第一輪漏的），
但它們共享同一組偏誤，不等於獨立驗證。

## 實務建議：分區平行審計

規則數量大時（數百條），單一 agent 的輸出會超過限制。建議分區：

```
區塊 A：使用者層入口檔 + 設定檔
區塊 B：最大的專案指令檔（可能要再分段）
區塊 C：其他專案檔 + 記憶檔
區塊 D：跨檔衝突與重複獵捕（專門找 A/B/C 之間的矛盾）
區塊 E：安全、注入、能力、循環（專門找危險類）
區塊 F：completeness critic（專門找「大家都漏掉的位置」）
```

**F 區塊最容易被省略，但它抓到的東西往往最重要**——
例如所有人都在審 `CLAUDE.md`，沒人發現旁邊還有個同樣大的 `AGENTS.md`。

### 輸出超限的處理

若單一區塊規則太多導致輸出被截斷：
1. **不要假裝完成**
2. 改用分段策略（例：按章節切成 3 段）
3. 在報告中誠實標示「某區塊未完成，已改分段補跑」
4. 補跑完成後回填，並更新驗證項

## 交叉審查時的裁決原則

當兩份審計結論不同：

| 情況 | 採用 |
|---|---|
| 一方有實測證據，一方是推測 | **有證據的** |
| 一方說「安全」一方說「有風險」 | **從嚴**（除非有證據證明無風險） |
| 一方說重複、一方說範圍不同 | 看實際載入路徑——**同一 session 會同時載入才算重複** |
| 一方要刪、一方要留 | 預設**留**，除非刪的一方能指出替代規則 |

記錄裁決時必須寫：衝突內容／採用哪一條／為什麼／被取代規則如何處理／
是否需要人工確認。
