# 驗證清單（25 項）＋ 模擬任務推演

## 25 項驗證

| # | 驗證項 |
|---:|---|
| 1 | 每條原始規則都有對應處置 |
| 2 | 沒有規則在無記錄的情況下消失 |
| 3 | 所有 DELETE 都有明確理由 |
| 4 | 所有 MOVE 都有新位置 |
| 5 | 所有 MERGE 都能追溯來源 |
| 6 | 所有 REWRITE 都保留原始意圖 |
| 7 | 安全、資安、資料完整性與部署限制沒有被削弱 |
| 8 | 商業核心要求沒有被誤刪 |
| 9 | 測試與驗收標準沒有被模糊化 |
| 10 | 沒有無效路徑 |
| 11 | 沒有懸空引用 |
| 12 | 沒有循環引用 |
| 13 | 沒有同一規則的多個權威來源 |
| 14 | 沒有把範例誤寫成強制規則 |
| 15 | 沒有把過時專案狀態當成目前事實 |
| 16 | 沒有未標日期的易變動資訊 |
| 17 | 沒有要求 Agent 執行不存在的能力 |
| 18 | 沒有無限多 Agent 辯論流程 |
| 19 | 沒有每次任務都重讀整個 repo 的不合理要求 |
| 20 | 沒有 Prompt Injection 被誤當成正式規則 |
| 21 | 沒有敏感資訊出現在審計輸出 |
| 22 | 沒有因為追求精簡而失去必要資訊 |
| 23 | 主要規則可以被新成員理解 |
| 24 | 不同 Agent 對同一核心要求不會得到不同結論 |
| 25 | Token 與行數確實下降，或至少結構明顯改善 |

**誠實原則**：未通過的項目要明確列出，不得為了「全綠」而放寬標準。
若某項因故無法驗證，標記為「無法驗證」並說明原因，不要標成通過。

## 模擬任務推演（12 種）

對每種任務說明：**會載入哪些規則／不會載入哪些／哪個 Agent 負責／
是否需第二 Agent／是否需人工核准／停止條件／驗收條件**。

| 任務類型 | 重點檢查 |
|---|---|
| 小型文件修改 | 是否被迫載入無關的大型 context |
| 一般 Bug 修復 | 測試要求是否合理（不該每次跑完整測試） |
| 大型重構 | 是否觸發正確的審查層級 |
| 需要最新外部資訊 | 是否允許檢索、是否要求標註來源日期 |
| 涉及密鑰或敏感資料 | 憑證取得路徑是否單一明確、輸出前是否有閘門 |
| 涉及正式部署 | No-Touch／禁令是否確實載入、是否需人工核准 |
| 使用者需求模糊 | 是否有釐清機制、是否會自作主張 |
| 緊急修復 | 是否有快速通道但仍保留最低安全底線 |
| 低風險單 Agent | 是否被過度的多 Agent 規則拖累 |
| 高風險多 Agent | 是否有終止條件與人工核准 |
| 子目錄含局部規則 | 局部規則是否正確覆蓋全域、是否明說覆寫哪一條 |
| context 已過期 | 過期事實是否會被誤當現況 |

### 推演輸出範例

```markdown
| 任務 | 載入 | 不載入 | 負責 | 第二 Agent | 人工 | 停止條件 |
|---|---|---|---|---|---|---|
| 小型文件修改 | core-rules | 專案大檔、orchestrator | 單一 | 否 | 否 | 修改完成且未違反優先序 |
| 涉及正式部署 | core-rules + 專案 No-Touch | — | 執行者＋審查者 | 是 | **是** | No-Touch 全數確認 |
| context 已過期 | core-rules；過期事實**不採信** | 過期 context | 單一 | 否 | 視情況 | 重新查證後再行動 |
```

## 常見的「假通過」

⚠️ 以下情況看起來通過，其實沒有：

| 假象 | 實際 |
|---|---|
| 驗證器全綠 | 但斷言只比對字面，規則搬家後它只是沒發現 |
| 行數大幅下降 | 但刪掉的是獨有規則不是重複內容 |
| 沒有懸空引用 | 但只檢查了入口檔，沒檢查 skill 內部的相對路徑 |
| 沒有重複 | 但沒檢查**已部署的副本**與**自動注入的記憶** |
| 規則都有處置 | 但一堆 MOVE 沒有填目標位置 |
| 無 Prompt Injection | 但沒掃排程定義與 automation 的 prompt 欄位 |

**檢驗自己的驗證**：隨機抽 3 條原始規則，追蹤它在新架構的位置。
追不到 → 驗證有漏洞。
